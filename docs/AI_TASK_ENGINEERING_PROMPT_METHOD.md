# AI 协作方法论：Prompt Engineering 的本质是任务工程

**记录日期：2026-09-27**  
**性质：** 方法论笔记 / AI 协作习惯 / 申请与长期工作方式记录

## 核心判断

真正重要的不是“会写神奇 Prompt”，而是会做**任务工程（task engineering）**。

Prompt 的价值不在于堆砌技巧、关键词或花哨格式，而在于把脑中的模糊需求压缩成一份别人可以独立执行的任务说明。对复杂任务而言，一个高质量 Prompt 更像：

- 高质量工单；
- 实验 protocol；
- 项目 brief；
- SOP；
- 给组员的任务分解。

它的目标不是让人和 GPT 聊得更多，而是让人能够**一次把任务交代完整，然后离开**。

---

## 一个重任务至少需要七个部分

### 1. 目标清楚

先定义最终到底要什么结果，而不是只描述“想研究什么”。

例如不要只说：

> 帮我查日本应用物理。

而要明确：

> 找到 2027 秋可申请、材料本科可入、英语入口可用、偏测量/反演/算法的导师。

### 2. 范围清楚

明确查哪些、不查哪些。

范围越清楚，GPT 越不容易无限扩展，也越容易真正完成任务。

### 3. 标准清楚

提前定义：

- 什么算保留；
- 什么算淘汰；
- 什么算证据不足；
- 什么情况下需要人工确认。

这相当于科研里的 inclusion / exclusion criteria。

### 4. 输入完整

文件、已有结论、历史判断、约束和已完成工作尽量一次给够。

很多所谓“Prompt 不好用”，其实不是措辞问题，而是上下文不完整。

### 5. 自主权清楚

明确哪些小歧义允许 AI 自行处理，哪些关键决策必须由人决定。

例如：

> 一般歧义自行处理，不中途问我；只有会改变任务定义或结论边界的问题才需要停下来。

这能显著减少反复确认造成的中断。

### 6. 停止条件清楚

定义做到什么程度算完成。

例如：

> 扫完这 10 所学校即停止。

没有停止条件的重任务很容易变成无限搜索、无限优化、无限补充。

### 7. 交付格式清楚

提前说明最终要：

- 表格；
- 结论；
- 代码；
- 修改稿；
- GitHub commit；
- 行动清单；
- 新增 / 修正 / 删除 / 待确认四类结果。

这样 GPT 才能围绕最终产物组织过程，而不是只输出一段“看起来很聪明”的分析。

## 一个典型例子

### 模糊任务

> 帮我查一下日本应用物理。

### 任务工程化之后

> 仅查这 10 所学校，目标是找 2027 秋可申请、材料本科可入、英语入口可用、偏测量/反演/算法的导师。排除纯湿实验和重笔试项目。与现有表查重。一般歧义自行处理，不中途问我。扫完这 10 所即停止。最终只输出新增、修正、删除、待确认四类，并附官方证据。

两者真正的差异不是字数，而是第二个 Prompt 已经把：

[
	ext{模糊愿望}
ightarrow
	ext{可独立执行的任务}
]

完成了转换。

## Prompt Engineering 与科研训练其实是同一种能力

这件事和科研中的很多工作高度同构：

[
	ext{Prompt}
approx
	ext{实验方案}
approx
	ext{SOP}
approx
	ext{组员任务书}
]

科研中需要提前定义：

- 研究问题；
- 控制变量；
- 纳入和排除标准；
- 数据来源；
- 评价指标；
- 停止规则；
- 输出格式。

AI 协作也是一样。

因此，真正值得培养的不是“如何找到一句神奇咒语让 GPT 变聪明”，而是：

> **如何把复杂目标拆成边界明确、证据充分、可验收、可独立执行的任务。**

这是一种项目管理、科研设计和沟通能力，而不只是 Prompt 技巧。

## 为什么重任务尤其需要高质量 Prompt

简单问题：

> 这个公式是什么意思？

随口问就够了。

但复杂任务，例如：

- 横扫 10 所大学并更新申请数据库；
- 系统核验一批论文与期刊；
- 阅读仓库并修改科研项目；
- 做一次完整文献审计；
- 修改 PPT、代码和 GitHub 文档；

如果任务定义不完整，后续就会不断发生：

[
	ext{补充要求}
ightarrow
	ext{纠偏}
ightarrow
	ext{重新执行}
ightarrow
	ext{再次确认}
]

于是使用者会产生一种错觉：

> “我必须一直盯着 GPT，不然它就会跑偏。”

实际上，这往往不是“AI 必须被持续陪伴”，而是**任务接口还没有被定义好**。

## Prompt 与“GPT 焦虑”

这里最重要的心理层面，不是追求“完美 Prompt”，而是建立清晰的任务边界。

如果每件重任务都依赖：

- 不断刷新回答；
- 不断追加一句；
- 害怕漏掉某个条件；
- 时刻检查 AI 有没有走偏；
- 一直围着对话窗口转；

那么 AI 会从提高效率的工具，变成新的注意力占用源。

更好的工作方式是：

[
oxed{
	ext{先想清楚}
ightarrow
	ext{一次性交代}
ightarrow
	ext{让系统执行}
ightarrow
	ext{按验收标准检查结果}
}
]

因此，高质量 Prompt 真正降低的不是“模型犯错概率到零”——任何 Prompt 都无法保证完美输出——而是：

- 减少反复对话；
- 减少临时纠偏；
- 减少遗漏条件；
- 减少对过程的持续监控；
- 把注意力重新还给真正的学习、科研和生活。

所以“避免 GPT 焦虑”的关键不是少用 GPT，而是把 AI 使用方式从：

> **持续陪聊式控制**

升级为：

> **任务定义 → 委托执行 → 结果验收。**

## 2026-09-28 补充：普通聊天中的重型任务容错工程

仅仅做到“目标、范围、标准、停止条件、交付格式清楚”还不够。

当任务同时包含：

- 大量网页检索；
- 多个文件；
- Excel / ZIP 等二进制文件；
- GitHub 读取与写回；
- 长时间、多阶段推理；
- 多个外部工具调用；

真正的风险往往不再是“AI 理解错了”，而是**执行链中的某个环节失败后，整个任务状态变得不可恢复**。

因此，对普通聊天中的长任务，应把 Prompt Engineering 进一步升级为：

> **任务工程 + 容错工程 + 状态恢复工程。**

### 1. 内部小批次，外部一次交付

“分批执行”不应该意味着每做 10 个对象就回来问用户一次“要不要继续”。

正确做法是：

1. AI 自行把对象拆成若干小批次，例如每批 10–20 个；
2. 每批完成后保存结构化检查点；
3. 自动进入下一批；
4. 用户原则上只负责开工和最终验收。

也就是说：

> **内部小批次，外部一次交付。**

分批的目的是降低失败半径，而不是把调度工作重新转嫁给用户。

### 2. 单点失败必须隔离

长任务里，一个网页打不开、一个导师资料不足、一次工具调用失败，都不应该让整项任务立即终止。

推荐规则：

> **单条失败 ≠ 整个任务失败。**

例如：

- 某个实验室官网 404；
- 某个页面遇到 Cloudflare；
- 某个对象暂时无法确认；
- 一次搜索结果质量不足；

应记录：

- 对象；
- 已尝试来源；
- 失败原因；
- 当前临时状态；
- 后续重试入口；

然后继续处理其他对象。

主体完成后，再统一重试失败项。

### 3. 检查点必须可恢复

每个批次至少保存：

- 当前任务标识；
- 输入基线；
- Git commit / 文件 SHA / 文件版本；
- 已完成对象；
- 每个对象的结论；
- 证据来源；
- 未解决项；
- 失败原因；
- 下一批起点。

目标不是“永远不失败”，而是：

> **失败后能够从最近状态继续，而不是从头再来。**

普通聊天不能被假设成永远稳定、无限持续运行的后台 Agent，因此“无人值守”的真正含义不是永久后台运行，而是**不需要用户充当人工批次调度器**。

### 4. 研究阶段与正式写入阶段分离

对于正式科研文件、主表、论文数据汇总、申请数据库等：

#### 研究阶段

- 正式文件只读；
- 新结论写入临时 CSV / JSON / Markdown / 中间表；
- 允许反复核验、重试和纠错；
- 不要边搜索边修改正式源文件。

#### 写入阶段

只有当：

- 研究主体完成；
- 失败项已统一处理；
- 字段规则已冻结；
- 结果通过内部一致性检查；

之后，才一次性修改正式文件。

修改后必须验证：

- 行数 / 样本数 / 对象数是否意外变化；
- 原有字段是否被误改；
- 只修改了任务允许修改的内容；
- 是否存在重复、丢行、错位；
- 输出文件能否正常打开；
- Git diff 是否符合预期。

原则：

> **大调查，小批次；大修改，一次性。**

### 5. 二进制文件不要通过超长 Base64 作为默认搬运通道

如果 XLSX、ZIP、模型文件或其他二进制数据已经能通过：

- GitHub connector；
- Files；
- 直接下载；
- materialize；
- 本地运行环境；

直接获得，就不要先转成超长 Base64，再把整段文本塞进代码中恢复。

超长 Base64 在长任务中容易出现：

- 截断；
- 丢字符；
- padding 错误；
- 复制不完整；
- 上下文污染；
- 解码失败。

而这种失败和真正的科研逻辑没有任何关系，却可能拖垮整条执行链。

如果必须编码传输：

1. 分块；
2. 校验每块长度；
3. 重组后做 hash / ZIP 完整性检查；
4. 验证文件可正常打开；
5. 再进入正式写入阶段。

### 6. 什么情况才值得中途叫用户回来

只有真正的“硬阻塞”才应该中断执行，例如：

- 权限或登录失效；
- 关键输入缺失；
- 同名对象存在无法消除的身份歧义；
- 两条硬约束彼此冲突；
- 必须由用户进行主观取舍才能决定结果；
- 继续执行可能覆盖或破坏正式数据。

以下情况不应该把用户叫回来：

- 单个网页打不开；
- 某条证据暂时不足；
- 某个对象无法确认；
- 一次工具调用失败但可以重试；
- 某一小批里有少量异常项。

这些都属于执行层问题，应优先由任务内部消化。

### 7. 普通聊天重型任务的推荐 Prompt 模块

以后遇到网页审计、文献核验、批量科研资料整理、仓库审查、Excel/GitHub 更新等任务，可以直接加入下面这一段：

> **无人值守 / 容错执行要求：**  
> 本任务在普通聊天中执行。不要把内部分批变成需要我逐批回复“继续”的流程。请自行把研究对象拆成小批次，并在每批完成后保存结构化检查点，然后自动进入下一批。单个网页、对象或工具调用失败时，记录失败项并继续后续任务，不得因此终止整个任务；主体完成后再统一重试失败项。研究阶段不要修改正式文件，全部研究完成并通过校验后再一次性写入。只有权限、关键输入缺失、无法消除的身份歧义、硬约束冲突或正式数据安全风险等硬阻塞才向我提问。

对于文件任务，再追加：

> **文件处理要求：**  
> 已能直接读取的文件必须直接读取；不要通过复制超长 Base64 来搬运 XLSX / ZIP 等二进制文件。若必须转码，必须分块并做完整性校验。文件传输失败时，不得继续假设该文件有效。

这一段的作用不是要求模型“更努力”，而是明确规定：

- 如何切分执行；
- 如何保存状态；
- 什么失败可以绕过；
- 什么失败必须停；
- 什么阶段允许改正式数据；
- 最终如何验收。

### 8. 最终的人机分工

对于这种重型任务，理想的人机关系不是：

> 用户持续盯着 AI → AI 每走一步等确认 → 用户不停充当调度器。

而应该是：

[
oxed{
	ext{用户定义目标与边界}
ightarrow
	ext{AI 自行分批、执行、保存、重试}
ightarrow
	ext{AI 一次性交付}
ightarrow
	ext{用户验收}
}
]

一句话：

> **用户只负责开工和验收，不负责监工。**


### 9. 强制防卡死：纯分析上限与最终收口

对于多对象、多网页、多阶段的重型任务，还要额外限制“纯分析循环”。否则即使资料已经查得差不多，执行器也可能在最终综合阶段不断继续分析而迟迟不交付。

必须采用以下硬规则：

1. **禁止连续进行超过 3 次纯分析而不产生可见中间结果。**
   连续 3 次分析后，下一步必须转为实际动作：保存阶段性结果、进入下一批、输出结构化结论、修改文件、机械校验或最终汇总。

2. **每完成 5–8 个对象必须形成一次结构化检查点。**
   至少记录对象、结论、证据、完成状态、未解决项和下一批起点。检查点一旦形成，不得因为后续个别对象失败而重跑整批。

3. **单个对象无法确认时标记“待复核”并继续。**
   页面失效、证据冲突、工具失败或资料不足都只能局部挂起，不能阻塞全任务。

4. **足够证据即停止搜索。**
   已有官方页面足以支持判断时，不为追求更多佐证继续无边界检索。

5. **第一轮核验完成后，禁止重新大规模搜索。**
   最终阶段只允许整合已有证据、处理明显冲突，以及对少量待复核项进行针对性补查。

6. **最终综合阶段再次出现 3 次纯分析时，必须立即强制收口。**
   停止新增搜索，用现有证据完成当前版本；不确定项保留“待复核”，然后完成正式交付、文件写回、机械校验和 GitHub 提交。

7. **已完成对象阶段性锁定。**
   除非出现直接冲突的新证据，否则不得无故重复审查。

8. **单次分析错误或工具错误只允许局部恢复。**
   从最近检查点继续，不得从头重跑整个任务。

可直接复制的 Prompt 模块：

> **防卡死 / 强制收口要求：**  
> 禁止连续进行超过 3 次纯分析而不产生可见中间结果。每完成 5–8 个对象，必须保存一次结构化阶段性检查点并自动继续。单个对象核验失败时标记“待复核”，记录缺失证据后继续，不得阻塞整体任务。已有足够官方证据时停止继续扩展搜索。完成第一轮核验后禁止重新进行大规模学校/院系级扫描，只允许针对少数待复核项补查。最终综合阶段若连续出现 3 次纯分析，立即停止新增搜索并用现有证据强制收口，完成最终结果、文件修改、机械校验和 GitHub 写回。已完成对象不得无故重复审查；任何单次分析或工具错误只允许局部恢复，不得从头重跑整个任务。

推荐执行链：

> **分批核验 → 5–8 个对象一个检查点 → 单点失败挂起 → 主体完成 → 强制收口 → 一次性写入 → 机械校验 → GitHub 提交。**


### 10. 大输出禁止：上下文也是有限资源

重型任务除了要防止“无限分析”，还要防止**工具输出把上下文撑爆**。

典型危险操作包括：

- 直接打印整张 Excel；
- 输出完整 NDJSON / JSON；
- 打印完整 DataFrame；
- 把整页网页正文全部回显；
- 把超长 Base64 当作中间传输结果；
- 输出数百行调试日志。

这些操作会造成：

- 上下文膨胀；
- 后续解析变慢；
- 工具结果截断；
- 流恢复失败；
- 任务已经做完大部分，却在最后文件处理阶段卡死。

必须遵守：

1. **禁止把整个工作表、完整 JSON / NDJSON、完整 DataFrame、完整网页正文、超长 Base64 或大段日志直接输出到聊天。**
2. **大数据只在工具内部处理。**
   对话层只返回：必要字段、统计摘要、异常项、目标记录、检查点信息。
3. **Excel / CSV 任务必须定向读取。**
   优先按列、行、筛选条件和目标对象读取；即使需要全表处理，也不要把全表回显。
4. **禁止使用 `print(full_json)`、`print(df)`、`print(out.ndjson)` 等完整倾倒方式。**
5. **任何单次工具输出都要控制规模。**
   如果预期输出很大，应在工具侧先过滤、聚合、切片或保存到临时文件。
6. **如果大输出已经导致失败，只局部恢复。**
   保留此前检索与分析结果，从最近检查点或当前文件处理阶段继续，不得从头重跑。

可直接复制的 Prompt 模块：

> **大输出禁止要求：**  
> 禁止将整个工作表、完整 NDJSON / JSON、完整 DataFrame、完整网页正文、超长 Base64 或大段日志直接打印到聊天上下文。所有大数据应在工具内部处理，只返回本任务真正需要的字段、摘要、异常项或少量目标记录。Excel 只定向读取必要列和目标行；不得使用 `print(full_json)`、`print(df)`、`print(out.ndjson)` 等方式倾倒完整对象。若预计单次输出过大，必须主动截断并改为摘要读取。若已因大输出导致工具或流失败，应保留此前检查点，从当前阶段继续，不得重跑整个任务。


### 11. 终局写回锁：完成业务后必须立即执行写动作

长任务最常见的最后一类拖延，是业务已经完成、文件也已经校验，却在“最后写回”阶段继续反复思考。

因此必须加入**终局写回锁**：

1. **一旦状态明确为“只剩文件写回 / commit / 上传 / 保存”，立即锁定业务结果。**
   不得重新分析业务内容，不得重新搜索，不得重新计算已校验文件。

2. **终局写回阶段最多允许 1 次纯分析。**
   这一轮只能用于确认 HEAD、路径、冲突、文件版本和写工具。之后必须：
   - 调用实际写工具；或
   - 报告明确阻塞。

3. **禁止连续多个“已分析”而没有写动作。**
   已知仓库、目标文件和路径后，不得继续讨论实现方案。

4. **写回错误只能局部恢复。**
   只处理上传、commit、ref、权限、冲突或文件写入错误；不得退回前面的研究、排序或数据重算阶段。

5. **多个最终文件需要保持一致时，应优先原子提交。**
   如果工具无法保证原子性，应明确说明并停止在安全边界，而不是提交半套结果。

可直接复制的 Prompt 模块：

> **终局写回锁：**  
> 一旦任务进入“只剩文件写回 / commit”阶段，立即锁定业务结果，禁止继续重新分析、重新搜索或重新计算已校验文件。终局阶段最多允许 1 次纯分析，仅用于确认 HEAD、路径、冲突和写工具；下一步必须实际执行写回，或明确报告具体阻塞。若写回失败，只处理 GitHub / 上传 / commit / ref / 冲突问题，不得退回业务分析。若涉及多个最终文件且要求一致状态，应优先一次性原子提交，避免半完成写回。


### 12. Persistent Checkpoint / Crash Recovery：把长任务设计成可恢复系统

对于研究、网页审计、批量文件处理、Excel/GitHub 写回等长任务，最危险的假设是：

> “只要聊天还活着，状态就还在。”

这不是可靠的状态管理方式。成熟的任务工程必须把**持久化检查点（persistent checkpoint）**和**灾难恢复（crash recovery）**设计进任务本身。

#### 何时必须启用 checkpoint

满足以下任一条件时必须启用：

- 预计运行超过 20–30 分钟；
- 涉及 20 个以上对象；
- 需要大量网页检索；
- 需要修改正式文件或 GitHub；
- 中间结果无法轻易重新获得；
- 最终输出依赖大量前置判断。

#### 真正的 checkpoint 必须跨会话存在

以下内容不能作为唯一状态保存：

- 模型上下文；
- “已分析”状态；
- 临时 Python 变量；
- `/mnt/data` 中唯一存在的文件；
- 尚未 commit 的最终文件。

真正的 checkpoint 应写入：

- GitHub Markdown / JSON；
- CSV / JSON 结构化记录；
- 持久文件库；
- 临时分支；
- 明确命名的恢复文件。

#### 推荐保存频率

- 每完成 5–8 个对象；
- 每完成一个明确阶段；
- 进入最终文件生成之前；
- 进入最终 Git 写回之前。

每个 checkpoint 至少保存：

- 当前任务与阶段；
- 输入基线；
- Repository / Branch / HEAD；
- 文件 SHA / 版本；
- 已完成对象；
- 结构化结论；
- 证据；
- 待复核项；
- 已生成文件；
- 下一步。

#### 研究结果与最终文件解耦

正确架构：

> **Research → Structured audit state → Rendered artifact**

也就是：

> **研究 → 结构化审计结果 → Excel / DOCX / PPTX / 其他正式产物**

最终文件只是“渲染层”，不应该是唯一真相来源。

#### 终局前必须保存恢复包

进入最终写回阶段前，应保存一次完整恢复包，确保即使聊天在 commit 前崩溃，也能从新会话完成：

> **读取 checkpoint → 必要时重建文件 → 校验 → commit**

而不是重新进行研究。

#### 灾难恢复流程

出现会话、流、工具或运行环境崩溃时：

1. 读取当前 Git HEAD；
2. 读取最近 checkpoint；
3. 判断已完成阶段；
4. 只补 checkpoint 之后的缺口；
5. 对少数缺失项定点补查；
6. 必要时重建最终文件；
7. 校验；
8. 写回；
9. 回读验证。

禁止因为会话失败而重新执行全量研究。

#### 最终原则

真正可靠的无人值守任务，不是“永不失败”，而是：

> **失败时，最多损失最近一个小批次。**

因此：

> **Recoverability > One-shot completion.**


---

## 最终原则

可以把这一整套思想压缩成一句话：

> **Prompt engineering 的本质，不是学习如何对 AI 说话，而是学习如何把自己的意图工程化。**

再进一步：

> **真正成熟的 AI 使用者，不是最会和 GPT 聊天的人，而是最会把任务定义清楚、把边界设好、把验收标准写明，然后让 AI 独立完成工作的人。**

这也是未来项目协作的默认原则：

[
oxed{
	ext{少一点 Prompt 魔法}
+
	ext{多一点任务工程}
}
]

目标不是“完美控制 GPT”，而是让 GPT 成为一个边界清楚、可委托、可验收的执行系统。


#### 批量对象禁止逐行打印

除了禁止完整表格/JSON 倾倒，还必须禁止另一种隐蔽的大输出：**循环逐行打印批量对象**。

规则如下：

- **禁止使用 `for ...: print(...)` 将整批导师、论文、样本、候选项、文件记录逐条打印到聊天。**
- 批量对象必须在工具内部完成筛选、排序、匹配、聚合、去重与统计。
- 对话层只返回：
  - 分组计数；
  - 最终名单；
  - 排序结果；
  - 异常项；
  - 极少数必要样例。
- 若确实需要查看原始记录，只能定向输出少量目标对象，不得整批回显。
- 数据已经读入内存后，不得为了“检查”而再次全量循环打印；应直接在内存中完成后续处理。
- 一旦发现代码准备输出数十条以上对象，应改成摘要、切片、统计或写入检查点文件。

可直接复制的 Prompt 模块：

> **批量输出限制：**  
> 禁止通过 `for ...: print(...)` 等循环把整批导师、论文、样本或候选项逐行输出到聊天。批量数据必须在工具内部完成筛选、排序、匹配、去重和聚合，只向对话返回分组计数、最终名单、异常项和必要的极少数记录。若数据已经读入内存，不得为了检查而再次整批打印；应直接继续处理和收口。
